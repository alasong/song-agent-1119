## 0. 一句话

把任何事都看成一个目标节点（**go**）：**先确认目标，再把"做成它需要什么"递归就绪——不是开头做一次，而是每一步都做一次——然后拆成子目标、逐个执行；每个节点过三道门（输入 / 过程 / 结果），直到结果达成并收尾**。

这套逻辑的特征不是"流程多"，而是两件事：

1. **依赖先于行动**——事情做不好，多数不是执行差，是前提没就绪；
2. **每一步都在想依赖**——目标级和阶段级、步骤级用的是同一个动作，没有"上层想完下层照做"这回事。

## 1. 一个 go 的状态机

```
go(目标)
 ├─ A 目标确认      产出：清晰的目标陈述 + 验收判据 + 边界（不要什么）
 ├─ C 拆解确认      产出：拆解判据（什么算好拆解）
 ├─ B/D 交替        粗拆定依赖 → 依赖就绪 → 细拆；每轮必须收敛（见 §3.4）
 │    ├─ B 依赖优化  产出：依赖清单；每项标「就绪 / 复用 / 递归 go」
 │    └─ D 任务拆解  产出：子节点（各自可独立验收）
 ├─ E 逐节点执行    对每个子节点再跑一次 go（按依赖序，能并行则并行；每层过 §4 三道门）
 └─ F 收尾          产出：汇总验收 + 未完成清单 + 可复用资产入库
```

**A 不许自己确认**：目标的确认方是上一级节点或领导，系统只能提议"目标已清晰"并给出判据，不能自己给自己发开工许可。这条和"判据必须外部登记"是同一条红线的两个面。

两个展开动作要分清，它们是同一个节点的两种"变大"方式：

| 展开 | 回答的问题 | 子节点产出 | 失败症状 |
|---|---|---|---|
| **B 依赖优化** | 做成它，什么必须先就绪？ | 前提（工具 / 方法 / 流程 / 团队） | 没就绪就开干，中途反复返工 |
| **D 任务拆解** | 它的结果由哪几部分组成？ | 结果的一部分 | 拆得不重不漏，验收对不齐 |

**判据先于展开**：B 与 D 都不许"边想边拆"，先有判据（依赖怎么算就绪、拆解怎么算合格），再展开。这就是你说的"把方法搞清楚，本身又是一次依赖优化"。

## 2. 依赖优化（前置就绪）

### 2.1 定义

不是排优先级，而是问：**"要把这件事做好，什么必须先到位？"** 未到位的依赖，本身就是一个 go。

关键：依赖优化**不是一个阶段**（不是只在开头做一次），而是一个**动作**——节点级做一次，每个阶段、每个 step 开工前再做一次。目标级和 step 级用的是同一套问法与同一套质量判据（§2.7），区别只在粒度。

### 2.2 依赖清单（口述四类 + 兜底一类）

| 类 | 要回答的 | 就绪判据（可机检的部分） |
|---|---|---|
| 团队 | 谁做、够不够、分工是否覆盖目标 | 每个角色有职责与判据，且验证方独立 |
| 方法 | 怎么做才算对 | 有一条能判对错的判据；没有就先造判据 |
| 流程 | 按什么顺序、过哪些门 | 阶段有门，门有判据 |
| 工具 | 用什么执行 | 能跑通一条命令 / 取回真数据（不是"库里有这个工具"） |
| 其他 | 数据、权限、预算、环境 | 能取到、能授权、不超池 |

### 2.3 三个判定，按顺序，能省则省

```
需要吗？ ── 不需要 → 不建（防过度建设）
   │需要
现有够用吗？ ── 够 → 复用（防每个目标重建组织与工具）
   │不够
递归建（这个依赖 = 一个新 go） → 就绪后返回
```

第三条是"依赖优化可嵌套"的落点：依赖一个工具，就先把工具做好；依赖一个方法，就把方法优化；依赖一个组织，就把流程和组织建起来。

### 2.4 红线：组织必须 agent 化

凡依赖落在"人来做"，自动化链条就断在这里。人可以**定红线、批判据**（一次性动作），但不进执行环（每次动作）。判断口径：这个环节能不能无人值守连跑多轮——不能，就是没就绪。

### 2.5 嵌套、复用与环

- **嵌套**：依赖可以再依赖，深度不设死，但受 §5 的上限保护。
- **复用**：依赖产物入资产库（工具 / 判据 / 流程模板）。下一节点先查库，命中直接用——否则每个目标都在重建同一件工具。
- **依赖环**：A 需要 B、B 又需要 A，直接拒。环说明目标定义或拆法错了，退回上一层重定义，不许硬解。

### 2.6 B 什么时候算完成

依赖清单里每一项都有二值结论（就绪 / 复用 / 递归建），没有"待定"；清单自身无环；每一项都写了就绪判据。三条缺一条，B 不算完成——否则"依赖优化"会变成一个永远不收口的词。

### 2.7 依赖的质量：不是"有没有"，是"断言能不能验"

一条依赖只有写成**可证伪的一句话**，才算被真正想过：

| 字段 | 例子（工具类） | 反例（等于没想） |
|---|---|---|
| 断言 | 这条命令能在 30 秒内取回 A 数据 | 工具已就绪 |
| 验法 | 现在跑一次，看退出码与返回条数 | 库里有这个工具 |
| 若假 | 换 Y，或先造工具（成为子 go） | 到时候再说 |

**就绪 = 断言已验证为真**，不是"有这个东西"。二值的有/没有会把质量问题藏起来：工具在库里但取不到数据、方法写在文档里但判不了对错、人都到位但没人有判据——这三样都叫"没就绪"，但在清单上看起来是绿的。

四类依赖各自的质量维度：

| 类 | 质量问法 | 可机检的信号 |
|---|---|---|
| 工具 | 它真能干活吗 | 跑通一条命令 / 取回真数据 / 有失败信号 |
| 方法 | 它真能判对错吗 | 有判据，且判据在对抗样本上抓过错 |
| 流程 | 它真能防混过去吗 | 每段有门、门有判据、失败只重做一格 |
| 人 / 角色 | 他真能交付吗 | 有 duty + criteria、有战绩、验证方独立 |

## 3. 任务拆解

### 3.1 先定"什么算好拆解"

拆解前先确认拆解判据，这本身是一次依赖优化（依赖"拆解方法"）。没有判据就拆，等于边拆边改标准。

### 3.2 好拆解的判据

| 判据 | 怎么判 | 不满足就 |
|---|---|---|
| 覆盖 | 子节点的判据合起来能推出父目标的判据 | 补子节点或改拆法 |
| 互斥 | 子节点交付物不重叠（重名 / 同交付物即拒） | 合并或重切 |
| 可验收 | 每个子节点有自己的判据与交付物 | 重切，不许留"半个步骤" |
| 可排序 | 子节点依赖是有向无环 | 建依赖图，找环 |
| 粒度合适 | 一个子节点能在一轮预算内收口 | 收不了就继续拆 step |

### 3.3 反例（要能识别出来）

- 按章节拆：形式对齐、验收不对齐——每节都写了，合起来判不过；
- 按人头拆：把组织目标当结果目标；
- 拆出"半个步骤"：任何一个人无法独立验收的子节点。

### 3.4 依赖与拆解的真实顺序是交替，不是先后

口述是"依赖就绪 → 拆解"，但"确认拆解标准"本身又依赖方法，两者会互相咬住。所以执行上是交替：

```
粗拆（够定依赖即可） → 依赖就绪 → 细拆 → 新依赖 → 就绪 → 继续细拆 …
```

**必须收敛**：每一轮要么节点数增加、要么不确定性下降；连续两轮没有变化即判停（说明拆法或目标有问题，退回 A）。

## 4. 三道门（每一层都有）

### 4.1 输入门（动手前）

判三件事：**目标清晰、判据已定、预算在**。任何一条不成立 → **零调用**，退回。

"依赖就绪"不放在这道门里判：A 确认时依赖还没展开（B/D 在后面），此时判它必然判假。依赖就绪由 §2.6 在 B 完成时定，并在进入 E 之前复检一次——那时依赖清单已经展开完，才判得准。

**每个 step 也过同一道门**：进入 E 的每个 step 开工前，先交本步的依赖断言（§2.7）；清单为空、断言不可验、或缺口没写 → 本步零调用。节点级那一次在 A 之后、E 之前；step 级那一次在每个 step 之前。两处用同一套字段，不许 step 级"简化成口头确认"。

### 4.2 过程门（执行中）

这是三道门里最贵、也最容易做成摆设的一道。五条约束：

1. **极简**：只判"要不要继续"，不判内容好坏（内容归结果门）。
2. **机判**：不靠人逐段看；人只在越界时被叫醒。（2026-11-24 领导确认：过程门 = 机判、不靠人逐段检查）
3. **分步检**：不做实时检查（成本太高），按 step 边界或每 N 步检查一次。
4. **可打断**：任意检查点都能停；已完成的步骤不重跑，恢复从检查点继续。（"打断"指停在**检查点**，不是任意一条指令都能停——任意停就等于没有过程状态。）
5. **长了就拆**：一个 step 内收不了口，就把过程继续拆成 step1 / step2 / step3，让每个 step 都能在一次检查里收口。

### 4.3 结果门（节点交付前）

判：节点判据全过 + 证据可定位。不过 → **只重做这个节点/这一格**，不重做整个父目标。

### 4.4 父节点的自检

子节点全绿 ≠ 父目标绿。父节点汇总时还要用自己的结果门复判一次（尤其"覆盖"判据）。这是"结果达成之后自己也有一个检查"的落点。

### 4.5 门的成本规则

| 门 | 检查频率 | 谁判 | 不过的代价 |
|---|---|---|---|
| 输入门 | A 后一次；E 前复检依赖 | 系统判；判据来自外部登记 | 零调用 / 退回准备 |
| 过程门 | 每 step / 每 N 步 | 系统 | 停或退回上一个检查点 |
| 结果门 | 每节点一次 | 外部判据的持有方 | 只重做该节点 |

所有门的判定都要进 append-only 账本（含拒收原因）；判定不入账，等于事后无法回答"它为什么停在这里"。

## 5. 递归、收敛与终止

- **同一个 go 在每层复用**：没有"子任务专用流程"。
- **执行顺序**：子节点按依赖拓扑序；互不依赖的可以并行。
- **回退规则**：哪个节点红就只重做哪个；父节点红但子节点全绿 → 问题在拆解或判据，回退到 C（拆解确认），不是重做执行。
- **终止条件**：无未就绪依赖 + 无未执行子节点 + 结果门通过。
- **四道保护**：预算、步数、深度、时长，任一越界即停并上报，不静默继续。
- **收尾不许空**：写清"做成了什么、没做成什么、哪些资产可复用"。

## 8. AI 为什么不会主动思考，怎么让它会

### 8.1 人为什么主动：三个条件，利益只是其中一个

1. **后果可感**：做不好当场疼（返工、挨批、丢单）；
2. **主体连续**：今天的我惦记明天的我，长期收益才有意义；
3. **动作空间清楚**：知道"要更好"该补哪一块。

利益驱动只是第 1 条的一种形式。少了 2 和 3，给多少奖励都白给。

### 8.2 AI 三条都不满足，所以"设 KPI"通常无效

| 条件 | 人 | 现在的 AI | 结果 |
|---|---|---|---|
| 后果可感 | 当下就疼 | 奖励记在账本里，这一轮感受不到 | 动作不变 |
| 主体连续 | 有 | 跨会话失忆（除非档案注入） | 远期收益等于别人的 |
| 动作空间 | 知道补哪 | 不知道"好"要补哪个依赖 | 只能做表面功夫 |

结论：**卡点不在动机强度，在"奖励"和"动作"之间没有连线**。补连线只能靠结构，不能靠劝。

### 8.3 四层机制：把"主动"变成不得不发生的事

**(1) 结构强制——不想就进不去**
每个 step 开工前必须交依赖断言单：本步产出、依赖清单（§2.7 三字段）、缺口。字段缺、断言不可验、缺口空着 → 本步零调用。这不是让模型更愿意想，是让"不想"进不去门。

**(2) 缺口驱动——把"想做好"翻译成差值**
每一步结束算 `gap = 目标质量 − 当前质量`（按外部判据算，不按自评）。gap 不降 → 换方法 / 换依赖 / 拆 step，不许沿同一条路继续跑。人靠"想把事做好"的意愿，AI 靠这个差值：机制不同，动作同构。

**(3) 同轮兑现——后果下沉到这一步**
断言验真 → 本步预算返还或下一步额度上浮；断言证伪 → 扣预算、记入失败库、同类依赖下一轮默认降级；漏报依赖（没写进清单、被结果门抓出）→ 双倍扣。关键在"同一轮兑现"：账本上 N 轮后才生效的奖励，对模型不是后果。

**(4) 选择压力——让会想的活下来**
同一目标并行 k 个依赖假设，用结果门 + 盲测淘汰；胜出的依赖模式入库（工具 / 判据 / 流程模板），下次先查库。这样"会不会主动想"成了可进化性状，而不是一次提示。

### 8.4 度量（三个数，缺一不可）

| 指标 | 算法 | 异常信号 |
|---|---|---|
| 依赖覆盖率 | 有可证伪断言的依赖数 ÷ 结果门回填的实际依赖数 | < 1 说明有依赖没被想过 |
| 断言命中率 | 验真的断言 ÷ 总断言 | 过高 = 只写稳的；过低 = 乱猜 |
| 依赖缺口发现率 | 被下游抓出的依赖缺口 ÷ 总依赖数 | 持续为 0 说明门太松或根本没人抓 |

零容忍项：step 级空断言单的比例必须为 0。

### 8.5 和现有设计的对应

- 设计文档 §15.2 已有主动性的四件承载体（常驻目标 / 心跳 / 自评 gate / 求助），缺的正是"依赖断言"这道工序；
- §15.8 有可失去性与自我档案，但惩罚是 N 轮后生效，对模型不可感——要补"同轮兑现"；
- DNA #8 有收益账本，但没有"断言对错"这个记账对象；
- sa2 现有预算闸（`core/budget.py`）、失败库（`memory/lessons.py`）、角色档案（`memory/profiles.py`），没有任何一处要求在开工前写依赖断言。

### 8.6 这套做法的边界（不假装）

- 产出的是"不可跳过的推理工序 + 可兑现的后果"，不是欲望；行为上等价于主动，机制上不声称它有好奇心。
- 可判的只有行为：无人提示时是否生成了依赖断言、是否检验、错了是否改。哲学意义上的"主动"不在这里判。
- 反例风险：把断言写成形式（"工具可用"）能骗过门。防它的不是更多提示，而是对抗样本——断言也要过"冒充件"测试，和判据的待遇一样。
