# sa 2.0：一个薄的不变层 + 三圈可自生成的载体

> 状态：骨架实现，端到端可跑（`python3 scripts/sa2_demo.py` 退出 0）。
> 与 sa 1.0（`xm/`）**并存**，不互相 import：1.0 继续跑六门验收，2.0 用来验证「重来骨架」是否成立。

## 0. 一句话定界

**能自生成的是「载体」，永不自生成的只有「判定权」。**

三个自生成回路（都在 `sa2/forge/`）：

| 回路 | 造什么 | 落点 |
|---|---|---|
| 造目标 | 把领导给的目标拆成可分别验收的子任务，每个子任务带维度 | `forge/goal.py` |
| 造组织 | 编制（角色/duty/criteria）+ 流程（阶段绑角色 + 阶段门） | `forge/org.py` |
| 造判据与工具 | 把文字判据实例化成可执行判据，并先过三反例自测 | `forge/criteria.py` + `core/judge.py` |

判据**造**在 forge，判在 core——这条缝就是「生成方不持有判定权」的物理形态。

**实测行数**（写在这里就不用再问）：`core/` 362 行（judge 169 / gate 105 / ledger 46 / budget 42）、
`forge/` 328 行、`loop/` 124 行、`memory/` 59 行，合计 890 行。
不变层比原先估的「约 500 行」更薄，因为四道门里有两道（判据可执行、不静默失败）复用的是
`judge` 已有的登记与执行记录，没有另起一套。

## 0.1 天花板：2.0 的上限更高，下限也更低

**上限由什么决定**：1.0 的上限是我写死的能力数量（6 门 + 9 条 DNA + 一任务一手写的判据）；
2.0 的上限是「它能造出多少种载体」× 「判定层能判得多细」。前者可以长，后者是固定的——
所以 2.0 的天花板确实更高，**但那不是已经更高，是允许更高**。

**下限也更低**：1.0 有 272 条测试覆盖的完整链路、知识库、真实模型接入、24 小时常驻；
2.0 现在只有 890 行、假模型、无知识库、没进 bench。功能上它明显更弱。

**唯一能判「更高」的读数**是自生成率（见 §8）：1.0 是 0（判据全手写），2.0 的 demo 也是 0
（规格写死），目标不是「有数」，而是「数上去且二审一致率不掉」。

**天花板的反向风险**：能造的东西越多，判定层承压越大。判定层一旦为了让生成物通过而放宽，
天花板不是变高，是塌了——所以 `judge` 的 authority 名单、判据的三反例自测这两处，
应该是 2.0 里最不该动的地方。

## 1. 为什么重来

1.0 的诊断（`docs/ACCEPTANCE.md`、`scripts/dna_audit.py` 的读数）：
- 6 道门全在**终点**判，中间没有任何门——所以「缺一节」「步骤 0 条」这类结构失败要跑到最后才发现；
- 判红就**整篇重写**，一次拒绝的代价是整篇 token（实测单 agent 4/4 判红，升级组队 38 次调用）；
- 编制与流程是 `stage × role` 全连接（`xm/scheduler.py:47`），阶段不绑角色；
- 判据是一任务一手写的脚本，任务之间没有共同语言。

2.0 的诊断只有一句：**缺的不是原则，也不是验收，是中间那一层「环」**。

## 2. 四层

| 层 | 内容 | 谁能改 |
|---|---|---|
| `sa2/core/` | 判定权（`judge.py`）、账本（`ledger.py`）、预算闸（`budget.py`）、四道过程门（`gate.py`） | 只有外部的判定权持有者；sa 只能读 |
| `sa2/forge/` | 目标拆解（`goal.py`）、编制与流程（`org.py`）、维度声明（`dims.py`）、判据实例化（`criteria.py`） | sa 自己造，产出要过门 |
| `sa2/loop/` | PDCA 环：声明 → 前置门 → 逐阶段（产出 → 阶段门）→ 交付门 → 证据门 | 逻辑固定，不随任务变 |
| `sa2/memory/` | 案例库（失败案例优先） | 只追加 |

## 3. 红线：生成方永不对判据拥有判定权

- `Judge(authority=("leader", "verifier"))`：`register()` 会检查 `proposer` 是否在名单里，生成方抢登记直接被 `Unauthorized` 拒。
- `forge/criteria.py` 只能 `propose` / `tested`，产出 `Criterion`，登记动作必须发生在判定权持有者那一侧。
- 自测三反例是登记的入场券：合格件必须过、缺件必须拒、**冒充件**（把标题塞进代码围栏）必须拒。
  第三件是实测教训——sa 1.0 的 `dna_audit.py` 首版就被自己的正则字面量和注释骗出 5 处误判。

## 4. 四道过程门

| 门 | 判什么 | 不成立会怎样 |
|---|---|---|
| G1 声明先于执行 | 目标/维度/判据/预算都在，维度在词表内 | 前置门不过，**一次调用都不发** |
| G2 判据可执行 | 已登记、形态合法、跑过三反例、不覆盖未声明维度 | 不许拿没验证过的判据验收 |
| G3 证据可定位 | 每条证据是 `path:line`（文件与行号真实）/命令/读数 | 证据门红 |
| G4 不静默失败 | 声明的维度有判据覆盖；声明的判据本轮真的被执行 | 交付门红（声明了没人读 = 承诺没兑现） |

## 5. 与 1.0 的关键差别

| | sa 1.0 | sa 2.0 |
|---|---|---|
| 派活 | `stage × role` 全连接 | 阶段绑角色，且编制层派活数必须 **<** 角色数 × 阶段数（`org.parse_plan` 直接拒全连接） |
| 判红代价 | 整篇重写 | **只重做该阶段**（下游没跑，上游不重来） |
| 判据来源 | 一任务一手写 | 从规格实例化 + 三反例自测 + 外部登记 |
| 门 | 6 道终点门 | 4 道过程门（终点门仍是 `bench.py` 的 6 条，两层不合并） |
| 维度 | 无 | 8 词值域 + 声明即须有判据覆盖 |

## 6. 怎么跑

```bash
python3 scripts/sa2_demo.py          # 端到端全环，含一次阶段拒绝
python3 scripts/sa2_demo.py --json   # 机器读
python3 -m unittest tests.test_sa2_core tests.test_sa2_forge tests.test_sa2_loop -q
```

demo 是**确定性假模型**（`Scribe`），故意让「成稿」第一次缺第三节，用来证明两件事：
拒绝只重做该阶段、证据门与交付门是分开的两道。

## 7. 现在还没做（写在这里，不是藏在代码里）

- **观点类判据不生成**：`forge/criteria.py` 只实例化结构类判据（章节齐不齐）。写得好不好仍要人定标准——生成方造这种判据等于自评。
- **真实模型未接**：demo 用假模型，避免用一次 API 调用假装证明架构。接真模型只需要把 `produce` 换成走 `xm.llm` 的实现。
- **知识库未接**：2.0 没有复用 `xm/kb.py`，边界是「不 import」，要接是独立一步。
- **没进 bench**：六门验收仍判 1.0；2.0 要替代它，得先证明三件事——自生成率、拒绝率、二审一致率（见 `docs/SA2.md` 下一节）。

## 8. 靠什么判断 2.0 真的更接近「会自生成」

三个读数，缺一个都不能说它更好：

1. **自生成率** = 由 sa 生成而非人写的判据条数 ÷ 总判据条数（现在 demo 里是 2/2，但判据内容是我在 demo 里写死的规格，不能算真自生成）。
2. **拒绝率** = 自生成物被门拒的比例。100% 说明生成太差，0% 说明门太松。
3. **二审一致率** = sa 生成的判据由独立验证方复跑，结果一致的比例。

现在这三个数都还没测。demo 证明的是**环能跑、门是活的、拒绝只重做一格**，不证明它已经会自生成。
