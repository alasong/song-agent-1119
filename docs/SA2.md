# sa 2.0：一个薄的不变层 + 三圈可自生成的载体

> 状态：骨架实现，端到端可跑（`python3 scripts/sa2_demo.py` 退出 0）。
> sa 1.0（`xm/`）已于 2026-11-20 **退役**，仓库里现在只有 2.0；退役记录见 §9.8。

## 0. 一句话定界

**能自生成的是「载体」，永不自生成的只有「判定权」。**

三个自生成回路（都在 `sa2/forge/`）：

| 回路 | 造什么 | 落点 |
|---|---|---|
| 造目标 | 把领导给的目标拆成可分别验收的子任务，每个子任务带维度 | `forge/goal.py` |
| 造组织 | 编制（角色/duty/criteria）+ 流程（阶段绑角色 + 阶段门） | `forge/org.py` |
| 造判据与工具 | 把文字判据实例化成可执行判据，并先过三反例自测 | `forge/criteria.py` + `core/judge.py` |

判据**造**在 forge，判在 core——这条缝就是「生成方不持有判定权」的物理形态。

**实测行数**（写在这里就不用再问）：`core/` 362 行（judge 169 / gate 105 / ledger 46 / budget 42）、
`forge/` 328 行、`loop/` 124 行、`memory/` 59 行，合计 890 行。
不变层比原先估的「约 500 行」更薄，因为四道门里有两道（判据可执行、不静默失败）复用的是
`judge` 已有的登记与执行记录，没有另起一套。

## 0.1 天花板：2.0 的上限更高，下限也更低

**上限由什么决定**：1.0 的上限是我写死的能力数量（6 门 + 9 条 DNA + 一任务一手写的判据）；
2.0 的上限是「它能造出多少种载体」× 「判定层能判得多细」。前者可以长，后者是固定的——
所以 2.0 的天花板确实更高，**但那不是已经更高，是允许更高**。

**下限也更低**：1.0 有 272 条测试覆盖的完整链路、知识库、真实模型接入、24 小时常驻；
2.0 现在只有 890 行、假模型、无知识库、没进 bench。功能上它明显更弱。

**唯一能判「更高」的读数**是自生成率（见 §8）：1.0 是 0（判据全手写），2.0 的 demo 也是 0
（规格写死），目标不是「有数」，而是「数上去且二审一致率不掉」。

**天花板的反向风险**：能造的东西越多，判定层承压越大。判定层一旦为了让生成物通过而放宽，
天花板不是变高，是塌了——所以 `judge` 的 authority 名单、判据的三反例自测这两处，
应该是 2.0 里最不该动的地方。

## 1. 为什么重来

1.0 的诊断（`docs/ACCEPTANCE.md`、`scripts/dna_audit.py` 的读数）：
- 6 道门全在**终点**判，中间没有任何门——所以「缺一节」「步骤 0 条」这类结构失败要跑到最后才发现；
- 判红就**整篇重写**，一次拒绝的代价是整篇 token（实测单 agent 4/4 判红，升级组队 38 次调用）；
- 编制与流程是 `stage × role` 全连接（`xm/scheduler.py:47`），阶段不绑角色；
- 判据是一任务一手写的脚本，任务之间没有共同语言。

2.0 的诊断只有一句：**缺的不是原则，也不是验收，是中间那一层「环」**。

## 2. 四层

| 层 | 内容 | 谁能改 |
|---|---|---|
| `sa2/core/` | 判定权（`judge.py`）、账本（`ledger.py`）、预算闸（`budget.py`）、四道过程门（`gate.py`） | 只有外部的判定权持有者；sa 只能读 |
| `sa2/forge/` | 目标拆解（`goal.py`）、编制与流程（`org.py`）、维度声明（`dims.py`）、判据实例化（`criteria.py`） | sa 自己造，产出要过门 |
| `sa2/loop/` | PDCA 环：声明 → 前置门 → 逐阶段（产出 → 阶段门）→ 交付门 → 证据门 | 逻辑固定，不随任务变 |
| `sa2/memory/` | 案例库（失败案例优先） | 只追加 |

## 3. 红线：生成方永不对判据拥有判定权

- `Judge(authority=("leader", "verifier"))`：`register()` 会检查 `proposer` 是否在名单里，生成方抢登记直接被 `Unauthorized` 拒。
- `forge/criteria.py` 只能 `propose` / `tested`，产出 `Criterion`，登记动作必须发生在判定权持有者那一侧。
- 自测三反例是登记的入场券：合格件必须过、缺件必须拒、**冒充件**（把标题塞进代码围栏）必须拒。
  第三件是实测教训——sa 1.0 的 `dna_audit.py` 首版就被自己的正则字面量和注释骗出 5 处误判。

## 4. 四道过程门

| 门 | 判什么 | 不成立会怎样 |
|---|---|---|
| G1 声明先于执行 | 目标/维度/判据/预算都在，维度在词表内 | 前置门不过，**一次调用都不发** |
| G2 判据可执行 | 已登记、形态合法、跑过三反例、不覆盖未声明维度 | 不许拿没验证过的判据验收 |
| G3 证据可定位 | 每条证据是 `path:line`（文件与行号真实）/命令/读数 | 证据门红 |
| G4 不静默失败 | 声明的维度有判据覆盖；声明的判据本轮真的被执行 | 交付门红（声明了没人读 = 承诺没兑现） |

## 5. 与 1.0 的关键差别

| | sa 1.0 | sa 2.0 |
|---|---|---|
| 派活 | `stage × role` 全连接 | 阶段绑角色，且编制层派活数必须 **<** 角色数 × 阶段数（`org.parse_plan` 直接拒全连接） |
| 判红代价 | 整篇重写 | **只重做该阶段**（下游没跑，上游不重来） |
| 判据来源 | 一任务一手写 | 从规格实例化 + 三反例自测 + 外部登记 |
| 门 | 6 道终点门 | 4 道过程门（终点门仍是 `bench.py` 的 6 条，两层不合并） |
| 维度 | 无 | 8 词值域 + 声明即须有判据覆盖 |

## 6. 怎么跑

```bash
python3 scripts/sa2_demo.py          # 端到端全环，含一次阶段拒绝（假模型）
python3 scripts/sa2_live.py          # 真模型跑一轮，读数带真实 usage
python3 scripts/sa2_demo.py --json   # 机器读
python3 -m unittest discover -s tests -t . -q
```

demo 是**确定性假模型**（`Scribe`），故意让「成稿」第一次缺第三节，用来证明两件事：
拒绝只重做该阶段、证据门与交付门是分开的两道。

## 7. 血肉：骨架之后还要补什么

骨架（890 行）证明的是「环能跑、门是活的、拒绝只重做一格」。它还**判不了内容、学不到教训、
断点不能续**——这六件是血肉，按「缺了就没法产出真实读数」排序，不是按难度排。

| # | 补什么 | 补在哪 | 完成判据（可判 0/1） | 状态 |
|---|---|---|---|---|
| 1 | 模型接入 + **拒绝后带失败原因重做** | `forge/scribe.py`、`loop/pdca.py` | 假 llm 下：提示词含「上次被拒的原因」、`verifier` 不产正文、`max_tokens` 透传、重做那一次确实收到 feedback | **已完成**（7+1 条测试） |
| 2 | 内容类判据 + 自测扩展 | `forge/criteria.py` | 一条内容判据（如「每条路径必须写机制/证据/止损」）能过三反例并被登记 | **已完成**：`必须出现：` → 字面 regex，围栏内不算 |
| 3 | 案例接回下一轮 | `memory/cases.py` + `loop/pdca.py` | 同一阶段第二次被拒时，提示词里出现上次案例 | **已完成**：`PDCA(cases=...)` 拒绝时查相似案例并入 feedback，最终失败时入库 |
| 4 | 断点与重入 | `loop/pdca.py` | 杀进程后能从最后通过的阶段继续，前面不重跑 | 未开始 |
| 5 | 与 bench 的接口 | `scripts/bench.py` 或 sa2 自己的跑分 | 六门或等价读数能对 2.0 跑出退出码 | 未开始 |
| 6 | 并行边界 | `loop/pdca.py`（阶段内角色） | 先给出「并行到哪一层」的判断 + 预算读数，再动代码 | 未开始，**不应先做**（会重演 1.0 的 38 次调用） |

排序理由一句话：**1 是前置**（没有真实调用与失败反馈，自生成率/拒绝率/二审一致率一个都测不出来）；
**2 和 3 决定它能不能判内容、能不能不重复犯错**；**4 和 5 是工程**；**6 最后**，且必须先有预算读数。

## 8. 靠什么判断 2.0 真的更接近「会自生成」

三个读数，缺一个都不能说它更好：

1. **自生成率** = 由 sa 生成而非人写的判据条数 ÷ 总判据条数（现在 demo 里是 2/2，但判据内容是我在 demo 里写死的规格，不能算真自生成）。
2. **拒绝率** = 自生成物被门拒的比例。100% 说明生成太差，0% 说明门太松。
3. **二审一致率** = sa 生成的判据由独立验证方复跑，结果一致的比例。

现在这三个数都还没测。demo 证明的是**环能跑、门是活的、拒绝只重做一格**，不证明它已经会自生成。

「还有用」不算——有用的东西放错层，比没用的更贵。

### 9.1 两处缺层（已落地）

1. **编制规模决策**。1.0 有「先单人、判不过再组队」；2.0 的环不管规模，永远按 plan 跑。
   该长在 **L2 开头**（一个 `size.py`：由声明与预算选规模），不该塞进 `forge`——
   它是**决策**，不是生成物；塞进 forge 就等于让生成方决定自己被验收多严。
2. **目标从哪来**。1.0 有 backlog（读进度表）+ resident（无人时自选）；2.0 假定有人给 goal。
   该长在 **L3**（`sa2/autonomy/`），且必须受 L0 约束：自己提的目标不能自己改判据。

两条现在已经补进代码：

- `sa2/loop/size.py`：`decide()` 按「预算下限 → 维度数 → 判据数」选规模，`single_plan()` 造
  一角色一阶段的编制，`plan_for()` 是唯一入口。默认单人与 1.0 的实测结论一致。
- `sa2/autonomy/`：`backlog.py` 管目标队列（自助目标必须 `approved=True` 才能领），
  `tick.py` 跑一轮「取目标 → 查判据是否已登记 → 跑环 → 落状态」。
  判据未登记就不开工——这是红线在 L3 的形态。

`memory/cases.py` 现在有包内消费者了（`PDCA(cases=...)`），不再是死功能。

### 9.2 真模型读数（2026-11-20）

`python3 scripts/sa2_live.py`：规模决策 single（预算 60000、单维度、2 条判据）→ 派活 1 次、
拒绝 0 次、**预算 604 tokens（真实 usage）**、证据门过、`passed=True`。
读数含义：通道与环在真模型上成立；这一轮没触发重做，所以「带着失败原因重做」仍只有假模型证据。

### 9.3 「造目标 / 造组织」真跑记录（2026-11-20）

在此之前，`forge/goal.decompose()` 与 `forge/org.plan_org()` **从未在真模型上跑过**——
实跑路径 `scripts/sa2_live.py` 只用了 `size` 的单人编制，demo 里那两份 JSON 是写死的。
补上 `--auto-goal` / `--auto-org` 之后连跑三轮，暴露并修掉两个缺口：

| 轮次 | 造目标 | 造组织 | 结果 |
|---|---|---|---|
| 1 | 4 个子任务 | 6 角色 / 4 阶段 | **崩**：阶段门引用了未登记的判据 → 同一阶段两次全红停机 |
| 2 | 3 个子任务 | 6 角色，被自己的校验拒绝（角色没派活） | 回退单人，passed（单人 3000 tokens） |
| 3 | 3 个子任务 | 6 角色 / 3 阶段 | 6 次派活、0 拒绝、passed（**15567 tokens**） |

修掉的两处：
1. `org.parse_plan(available_criteria=...)` + `pdca` 的前置门：**编制的阶段门必须落在已登记判据里**，
   否则一次调用都不发（第 1 轮那种空转本来是可以避免的）。
2. `org.plan_org(attempts=2)`：被自己的校验拒了要**带着拒收原因重来**，否则生成方只会重复同一个错。

三轮的成本对照是这一节最值钱的读数：同一任务，单人 **1843 tokens / 1 次派活**，
自生成六角色编制 **15567 tokens / 6 次派活**（约 8.4 倍）。值不值取决于交付质量差，
而这需要人工比对两份产物，不是自动能判的。

**仍未解决的弱点**：已登记的判据只有文档级两条，所以模型把每条阶段门都填成了
「关键要素 / 章节齐全」——中间阶段的产出被迫长成完整文档才算过。真正的分层需要
sa2 为每个阶段生成并登记对应判据，而这又回到「判据的原料由谁给」。

### 9.4 三个自生成回路全部接线（2026-11-20，含未解决项）

`--auto-goal / --auto-criteria / --auto-stages / --auto-org / --auto-tools` 五个开关都已接进
`scripts/sa2_live.py`，每个都真跑过。**已解决：**

| 回路 | 现状 | 真跑证据 |
|---|---|---|
| 造目标 | 每轮都出 3–4 个子任务（带维度与交付物） | `sa2-full6/subtasks.json` |
| 造判据 | 模型出「规格 + 最小合格样例」；整组四反例（含**空壳件**） | `sa2-full6/proposed_spec.md` |
| 造阶段判据 | 每阶段一组 `scope=stage` 判据，中间阶段不再被迫写成完整文档 | `stage-spec-*.md` |
| 造组织 | 6 角色 / 3–4 阶段，被自己校验拒了带原因重试 | `sa2-full6` 编制成功 |
| 造工具 | 生成 Python 检查器，三反例过了才准入；不合格的当场删除 | `sa2-full5/tools/stage1_checker.py` |

真跑过程中修掉的四个结构性缺口（都有回归测试）：
1. 阶段门引用了未登记判据 → 前置门拦下，一次调用都不发。
2. 生成方看不到本阶段的验收要求 → 要求随提示词下发（可见但不可改）。
3. 最后一个「定稿」阶段把前面正文整个丢掉 → 增加 `Stage.mode="append"` 装配语义。
4. 交付要求只挂在装配阶段 → 现在同时挂到「最后一个 replace 阶段」（真正写正文的人）。

**未解决（六轮同向失败后停手）**：全自动多阶段编制的**端到端判绿**没跑通。
最近一轮（`sa2-full6`）：10 次派活、3 次拒绝、28959 tokens，红在最后阶段——
模型自拟的文档结构（阶段判据）与我给的交付规格（六节）对不上，
每阶段都合规、整篇仍不合交付判据。

诊断：问题不在模型能力,而在**判据的来源与编制不同源**——交付判据来自外部规格，
阶段判据来自编制，两套结构必然打架。下一步应换方法（不是继续调提示词）：

- 要么**判据跟着编制走**：交付判据从「最后一个阶段的产出物描述」派生，而不是外部规格；
- 要么**限制为单阶段**：多阶段编制暂时只用于探索，交付仍走单阶段（这条已经能跑通）。

在这两件事定下来之前，`--auto-stages` + 外部规格 的组合不要用来自动交付。

### 9.7 重复章节修掉（2026-11-20）

现象：上一版交付里 `## ` 出现 26 次、同一章节重复，绿是公事公办的绿，不是好文档的绿。
根因不是判据松，是**每个阶段都在写整篇**，装配时首尾相叠。三条结构性修法：

1. **结构由一份样例定义，阶段只负责切片**（`criteria.plan_slices` / `slice_sample`）：
   交付样例的标题按阶段切分，互不重叠，`append` 拼起来自然不重复。
2. **一片只由一个角色执笔**（`pdca._writer`）：同阶段其它角色收到「不要写 ## 标题」的提示。
   实测没这条时，三个角色各写一遍，同一节出现 3 次。
3. **越界与重复由系统裁掉，不靠模型自觉**（`pdca._trim`）：只保留本阶段允许的标题、
   同一标题只留第一次出现。检查器加「重复章节 / 越界章节」两条，越界只对
   「从零写」的阶段生效（追加阶段的上游章节是合法的）。

真跑（`sa2-final/20261120-011056`）：**0 拒绝、passed=True**，交付 18,165 字节，
`## ` 标题 **6 个、6 个全唯一**，每节正文 550–1717 字，22,024 tokens 真实 usage。

**留下的诚实说明**：修法是「裁掉模型多写的部分」。如果模型在越界部分写了更好的一段，
系统会把它丢掉——结构干净了，代价是可能丢内容。要根治得让「每阶段只写一片」成为
模型真的愿意做的事（例如把阶段切片写进角色 duty），而不是靠事后裁。

### 9.11 ~~时效判据：说「最新」就得有日期~~（已撤回，2026-11-20）

> **撤回理由**：它读的是**模型自己写的日期**——模型把 `2025-05` 改成 `2026-11` 就绿了，
> 事实一点没变，等于让生成方给自己打分；而且它被硬编码挂在执行脚本里，判断时机在交付门
> （整轮跑完才发现）。留下来只会被当成资产，所以代码、测试、挂载一起删了。替代设计见 §9.12。

这一条不依赖任何外部能力——只用系统时间和交付里写的日期就能判，所以它排在「给手」之前。

| R3 | 最新日期距今 > 180 天 | 「最新」两个字是假的 |
| R4 | 出现未来日期 | 那是编的 |

### 9.12 证据原语：时间锚点必须由系统打戳（2026-11-20）

撤回 §9.11 之后，按「证据原语 → 手 → 引用判据 → 提示词」的顺序重做，本轮落第一块。

`sa2/core/evidence.py`：

| 概念 | 是什么 | 为什么这样 |
|---|---|---|
| `stamp()` | 把一次取回写成证据：内容按 sha256 落盘 + 系统时间打戳 | 模型无权写时间；没有内容就没有这条记录 |
| `Evidence` | `id / uri / fetched_at / content_path / digest / verifier` | 证据是**记录**，不是正文里的一句话 |
| `EvidenceBook.add()` | 入账前重算 digest、检查内容在盘、id 不重复 | 记录被改过就进不来；伪造的 id 也进不来 |
| `citation_problems()` | 正文里每个 `[S1]` 必须在台账里，且取回时间撑得起「最新」 | 判的是引用，不是文本日期 |

**判到哪里为止**：它证明「这条引用背后有一次取回，且内容与记录一致」；**不**证明内容为真、

### 9.13 证据链接线：第一次「带真数据且绿」（2026-11-20）

接线一次做完：手 → 派活 → 判据 → 提示词 → 读数。

| 环节 | 做了什么 |
|---|---|
| 手 | `sa2/fetch.py` 真查 arXiv；查询语句由模型写（题面里的缩写只有它分得清），剥成 ASCII、太长的布尔式退回短语重试；失败大声报，不返回空列表 |
| 派活 | `PDCA(hand=...)`：角色挂了工具就先跑一次手，取回内容落盘打戳成 Evidence，素材+编号进上游；`hand`/`hand_failed` 记进账本 |
| 判据 | `sa2/core/evidence:check_citations`，spec 自带台账路径与条数门槛（默认 3），judge 的 callable 判据现在可以把 spec 传进去 |
| 提示词 | 写手只许引上游给的 `[Sx]`；没有证据的地方不许写「最新」「近期」、不许编日期 |
| 读数 | `readings.json` 增 `evidence_count` / `citation_problems` |

顺手修掉一个真 bug：`register` 的幂等判断原来不比较 `dims`，于是跨运行复用同形判据时，
别轮的维度声明留在这一轮身上——实测导致前置门判红、0 次派活。现在 dims 一起比。

**真跑**（`rsi-ai/20261120-021401`，10,674 tokens）：5 个角色 / 3 阶段、0 拒绝、`passed=True`；
证据 7 条（`fetched_at` 全是系统打戳的 2026-11-20）、正文引用 `[S1]–[S6]` 共 74 处、
`citation_problems` 为空。

**但还有一处错位**：第一节标题是「最新进展」，内容却是「子问题清单 + 检索计划」——
因为它被分配给了第一个阶段，而那个阶段的职责是「问题拆解与检索计划」。切片按顺序分配，
标题与阶段语义不对齐，判据只查引用完整性、不查「这一节的内容配不配它的标题」。
下一步：切片按语义对齐（让阶段名与标题名匹配，或让规划器照着标题造阶段）。

### 9.14 复合题面四次真跑：绿是撑出来的，红才是真的（2026-11-20）

题面：「比较三条 AI 科研自动化路线（自动做实验 / 自动写作与审稿 / 自动选题），各给代表工作与
未解问题，最后给团队路线建议」。它与 9.13 那轮的区别就是「复合」：要三节互相依赖、要多个来源。

| 轮次 | 结果 | 死因或读数 |
|---|---|---|
| 1 | 红 | 取数零命中。`_simplify` 在查询本身已是短语时原样返回，降级降成原地不动 → 整轮死在 stage 2/3，2 次派活白花 |
| 2 | 红 | 生成的检查器把「标题下第一行是 `###`」当空章节，判红了两百多字的正文（用该脚本复现：带 `###` 的正文 rc=1，同样的正文去掉 `###` rc=0） |
| 3 | **绿** | 绿是假的：5 条证据是同一篇论文的 5 个副本（同 digest）；文档 22 个文献编号只有 1 个在台账里，另有张 39 行的表全凭记忆写；独立验证员输出 0 字符，阶段照过 |
| 4 | 红（对） | 去重 + 出处判据上线后：`引用 1 条 < 要求 3 条`。这篇题面的手只取回一篇论文，门就该红 |

四条修正（都在这一轮）：

1. **零命中真降级**：`_simplify_candidates` 按词数递减给候选（四词→三词→两词），逐个试，
   全不中才大声报错并带上试过的清单。
2. **检查器准入加正样例**：`_cases` 多一条「正文以 `###` 子标题开头」的合格件。子标题不算空节，
   检查器不接受它就在造的时候退回去，而不是等真活干到一半才判红。
3. **证据按内容去重**：`fetch.record` 见到已有 digest 就复用原 id。**更正 9.13 的「证据 7 条」**：
   那是 7 个副本、实际 3 篇（3 个 digest）——「至少 3 条引用」当时只靠 3 篇就过，不是 7 篇。
4. **新增 `交付·出处` 判据**：正文里出现的每个 arXiv id / DOI 都必须能在台账里找到。
   「引用标记在不在台账」查不到「整张表凭记忆写」，这条才是那个缺口。

顺手补：被拒的产出落进 `stages/rejected/<序号>-<阶段>-try<N>.md`。上面第 2 条的诊断
原本只能靠复现脚本猜——原因只留了一句字符串。

**结构边界（不是 bug，是设计）**：交付门在最末一次性判，红即整轮结束，没有「回到失败阶段重做」；
`forge/goal.decompose` 拆出的子任务只贡献维度并集，不各自成圈；`Role.tools` 里只有 `fetch:arxiv`
有实现。所以现在接的是「单源、三节上下、一次成稿」；接不了「多源、有依赖、要迭代、跨轮推进」。

### 9.14 三处尾巴收口（2026-11-20）

领导的要求是「每轮不留尾」，不是「把会话拉长」。三处一次清完，各自有读数。

**① 结构先行，阶段照章节造。** 原来先造编制再造交付样例，于是「问题拆解」阶段占了
「最新进展」那一节，正文写成检索计划。现在 `propose_spec` 提到 `plan_org` 之前，
`parse_plan(headings=...)` 校验「阶段数 = 章节数」，prompt 要求阶段名点明它在写哪一节。
真跑 `rsi-ai/20261120-083719`：阶段名 `最新进展章节：检索与整理 AI RSI 近期进展` /
`第二阶段：主要方向章节研判与撰写` / `第三阶段：风险与不确定性章节撰写与最终交付`；
第一节正文是真进展（Piccolo 论文、带日期与链接）。

**② 第二个源。** `sa2/fetch.py` 增 `hn()`（HN Algolia）与 `search()` 分发；手按角色挂的
**每件**工具跑一遍，每个源每轮只取一次。原来 `next(...)` 只取第一件手，台账 8 条全是 arXiv。
真跑台账：`arxiv.org` 6 条 + `marginalrevolution.com` 1 条 + `news.ycombinator.com` 2 条。

**③ 连续取数可复跑。** `scripts/sa2_fetch_stress.py`（默认 4 次、间隔 2s，失败即停）：
后台 6 次跑 `fails=0`、退出码 0；单次 1.03–37.51s，其中一次 37.5s 是慢请求触发了重试路径。

**顺手修的一处**：证据索引原来只有取数的那个角色看得到，后面的阶段拿不到可引用的东西，
于是正文只写得出 1 条引用、被判红。现在 `PDCA(context=...)` 每次派活都带上
「截至目前已取回的证据」，真跑引用 `[S1]–[S4]`、`citation_problems` 为空、`passed=True`。

### 9.15 知识面落地：世界知识是数据，机制是代码（2026-11-20）

上面 9.14 那轮修的都是「事故」，但每次事故都只能靠人改 `.py` 才能进系统——加一个数据源
要改 `fetch.py` 常量、拼 URL、写解析、再在宿主里登记三处；一条教训只能追加进同一个提示词
字符串，于是它对所有场景永远生效。根因不是某处写死，而是**知识唯一的进入通道是人改代码**。

这一版把通道换掉：

| 住哪 | 放什么 | 谁读 |
|---|---|---|
| `sa2/knowledge/data/sources.json` | 源的 host / URL 模板 / 解析器名 / 能力标签 / 查询风格 | `fetch`、宿主的工具清单 |
| `sa2/knowledge/data/vocab.json` | 维度词表、角色种类、能力词表、**事件空间（经验的条件值域）** | `dims`、`org`、`lessons` |
| `sa2/knowledge/data/formats.json` | 引用标记形态、文献编号形态（每条一个正则） | `evidence` |
| `sa2/knowledge/data/thresholds.json` | 阈值 + **出处**（值、来源、日期） | `config` |
| `sa2/knowledge/data/prompts/*.md` | 造检查器、引用规范的提示片段 | `forge.tools`、`forge.scribe` |
| `~/xm-runs/sa2/registry/lessons.jsonl` | 经验：`when` 条件 + 对策 + 命中统计 | `memory.lessons`（下一步接进 `_feedback`） |

装载器 `sa2/knowledge/loader.py` 的四条规则：缺文件/缺键/未知键/版本不认识 → 当场抛
`KnowledgeError`；顶层键白名单（写错一个键就红）；`sources` 的 host 必须在 url 里出现；
`thresholds` 每项必须带 `source` 与 `date`——没有出处的数不知道哪天该改它。

两个悬置点当场定死：

1. **解析器怎么解析**：显式注册表 + 名字（`sa2/parsers.py` 的 `PARSERS`），不做 importlib
   自动发现。靠反射猜约定已经在判据那层猜过一次（`judge._run_callable` 数参数个数），不重复。
   边界：同协议换站点改数据，换协议才加解析函数——让数据描述任意解析等于在 JSON 里写解释器。
2. **`when` 键域怎么定**：枚举白名单（`vocab.json.events`：`stage_kind` 7 个值、
   `failure_kind` 9 个值），写入与查询都校验。条件一旦可以自由拼文本，「按情境匹配」就退化成
   按关键词匹配，最后又变回一条全局规则。

**真跑验证接线**（`rsi-kn/20261120-091735`）：两只来源各取一次（arxiv 5 条、hn 5 条），
台账 9 条证据、9 个不同 digest，7 次派活、0 拒绝、`passed=True`、`citation_problems` 空。
交付 3 节、717 字，引用全部落在真实取回的 `[S1]–[S4]`。

还没做的：`evolution`（经验→机制候选，必须过 registry 登记）与 `lessons` 接进
`pdca._feedback`；运行期经验导出回仓库的脚本也还没写。
