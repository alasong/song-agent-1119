# sa 的目标架构

> 定位：`docs/ARCHITECTURE.md` 讲**现在长什么样**；本文讲**要长成什么样、差在哪、按什么顺序补**。
> 一句话目标：领导者只下任务，sa 自己决定「要什么人、按什么流程、怎么验收」，交付结果并自证最优。

---

## 1. 主链路（六段，缺一段就不叫组织）

```
目标 Goal
  → 组队 OrgPlan（要哪些角色、各给多少预算）
  → 定流程 Process（阶段顺序、谁交给谁）
  → 派活 Dispatch（按流程并发推进、角色间交接）
  → 验收 Verify（独立方按预先定好的判据判红/绿）
  → 沉淀 Settle（知识进底座、教训进案例库、账本留痕）
```

领导者只在 **Goal** 这一端出现，其余五段 sa 自己做。现在的实现只到「组队」的前半段。

---

## 2. 分层与职责（每层只做一件事）

| 层 | 组件 | 只负责 | 现状 |
|---|---|---|---|
| L0 目标层 | `goal_tree` | 把领导给的任务拆成可执行的目标树，定优先级与依赖 | **无**（读手写 ROADMAP 表） |
| L1 组织层 | `hiring` | 目标 → 角色、预算、流程；产出 `OrgPlan` | **有**（能生成，不能派） |
| L2 执行层 | `scheduler` + `worker` | 按 `OrgPlan` 派活、并发、交接、失败重派 | **半个**（daemon 单角色串行） |
| L3 判据层 | `criteria_runtime` | 把"文字判据"变成"可执行检查"并注册 | **无**（判据人写） |
| L4 记忆层 | `ledger` / `kb` / `self_model` | 可重放、领域知识、角色自我档案 | **只有账本** |
| L5 治理层 | `audit` / `approval` | 独立复核、熔断、淘汰、结构性变更审批 | **有定义**（verifier 角色） |

**关键约束**：上层只能通过下层的公开接口说话。执行层不许绕过判据层宣称成功，判据层不许由生成方自己改。

---

## 3. 五个对象（数据契约，先定这个再写代码）

| 对象 | 谁写 | 关键字段 | 不可变点 |
|---|---|---|---|
| `Goal` | 领导 | 目标、验收期望、预算上限、截止时间 | 下发后不可改，只能新增子目标 |
| `Role` | Super（L1 组队） | name、kind、duty、criteria、budget | 方案定稿后不可改；换人要新方案 |
| `Ticket` | 调度（L2） | id、sender、receiver、goal、evidence | 一旦提交只能追加状态，不能改内容 |
| `Criteria` | 专家 + 独立审批 | 名称、版本、检查方式（可执行）、阈值 | 生成方不能改；升格要过校准 |
| `Artifact` | 执行方 | 产物、证据链、判据版本、成本 | 只增不改 |

---

## 4. 怎么支撑"天花板无限"

天花板不在系统里，系统只负责**不设限**。三条机制：

1. **知识注入**：`researcher` 取回材料 → `curator` 只收已验证事实 → 进 `kb`。换领域 = 换知识源，不改架构。
2. **角色派生**：`OrgPlan` 不是固定六角色，是按目标动态生成的编制。新领域自然长出"该领域专家"这个角色。
3. **判据可扩展**：新领域自带验收方式——专家写判据、独立角色审判据。

**系统固定的是"怎么验收"，不固定"验收什么"。** 这一条是天花板能无限的前提：领域知识全在 L4，系统规则不随领域增长。

---

## 5. 怎么支撑"组织型、不漂移"

单 agent 会漂，因为它的状态在上下文里。组织靠四件事顶住：

| 机制 | 抗的是什么 |
|---|---|
| 判据外部化（生成方不能改） | 自评偏向自己 |
| 账本只增不改、可重放 | 说不清发生过什么 |
| 角色可替换（同一 Role 接口多实例轮换） | 单个角色变差拖垮全局 |
| 组织记忆（知识底座 + 案例库） | 换人/换会话就失忆 |

---

## 6. 防失控（硬约束，不靠自觉）

- 步数 / token / 时长三重熔断，任一触发即停并落读数
- 结构性变更（改判据、改流程、加角色类）必须人审
- 独立验证角色不得由生产方兼任（`hiring` 已强制）
- 高风险动作越级告警，不经中间层

---

## 7. 分阶段（每阶段一个可判红的能力）

| 阶段 | 补哪一层 | 判红判据 |
|---|---|---|
| M1 装配 | L2 雏形 | `Org` 跑通一单：提交→准出→拒收→重来，测试全绿 |
| M2 派活 | L2 | 按 `OrgPlan` 派给 ≥3 个角色、有交接、失败能重派 |
| M3 判据 | L3 | 把一条文字判据注册成可执行检查，且生成方改不动 |
| M4 知识 | L4 | 一个新领域：只换知识源，不改代码，能复现该领域一份结论 |
| M5 治理 | L5 | 杀掉主节点/实例，重建后继续；坏变更自动回滚 |

---

## 8. 现状 vs 目标（客观差距）

| 能力 | 目标 | 现状 | 缺口 |
|---|---|---|---|
| 目标拆解 | 自动生成目标树 | 读手写表 | 不会拆、不会排 |
| 组队 | 目标→编制 | 已能生成并机检 | 派不出去 |
| 派活 | 并发 + 交接 | 单角色串行 | 无调度器 |
| 判据 | 文字→可执行 | 人写死 | 无运行时 |
| 知识 | 自主获取 | 0 行 | 全空白 |
| 记忆 | 知识底座 + 自我档案 | 只有账本 | 缺两块 |

---

## 9. 三个未解难题（先摆在明面上）

1. **判据自动化**：开放式任务（判断好坏、选方向）的判据仍要人写。M3 只能做到"人写模板 → 系统实例化"，不是"系统自己发明判据"。
2. **编制最优性**：`OrgPlan` 能机检"要素齐不齐"，检不了"这个编制是不是最好的"。短期靠跑对比，长期靠案例库。
3. **成本**：并行组织的 token 成本可能超过收益。需要一条硬规则——**组织的成本上限必须由领导在下发任务时给定**，否则会烧钱换幻觉。
