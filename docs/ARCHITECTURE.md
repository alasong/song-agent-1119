# 架构

> 配套：`README.md`（边界与用法）、`ROADMAP.md`（执行顺序）。这里只讲「谁管什么、按什么顺序做事」。

## 1. 五层，各管一件事

```
原则层   7+1 条 DNA（不可运行时篡改）
  │      目标锚定 / 可度量 / 可编排 / 可观测 / 可回滚 / 自演化 / 腐烂检测 / 激励对齐
  ▼
判据层   tests/ —— 机器可判的红与绿。一切「完成」只认这个
  │
  ▼
执行层   xm/daemon.py —— 派活 → 改产物 → 跑判据 → 绿则收工，红则返工
  │      xm/runner.py —— 无进展检测：连续无产出 → 降级 → 冻结
  ▼
记忆层   xm/ledger.py —— append-only JSONL，只有审计方写
  │      xm/criteria.py —— 判据注册表，升格需过校准
  ▼
治理层   xm/gates.py —— 阶段准出；xm/pipeline.py —— 装配成流水线
```

## 2. 一次任务的生命周期

```
dispatch（派活）
  → 拼 prompt：规格 + 当前产物 + 上一轮失败输出
  → 模型返回代码块
  → 写入 target_file（**必须在 runs/ 下**，否则 DaemonConfig 直接拒绝）
  → 跑验收测试，拿 rc
  → rc=0 记 completed，收工
  → rc≠0 记 rejected（带失败用例名），把失败信息回灌下一轮
  → 连续 patience 轮无进展 → downgrade（提示降复杂度）
```

每一动作都落一条账本记录。账本里 `seq` 连续、只增不改，所以事后能重放整次运行。

## 3. 关键决策与理由

| 决策 | 用什么换来的 |
|---|---|
| 产物只能写 `~/xm-runs`（项目外），项目目录只由人审改 | 防污染：越界直接抛错，不靠自觉；任务判据（check.py）也跟着任务走 |
| 一次性任务的判据不进项目 `tests/` | 项目测试套件只放长期判据，任务产物与任务判据都在 `~/xm-runs/<任务>/` |
| 账本只有审计方（role="auditor"）能写 | 防刷账：被考核方自记账，读数就不可信 |
| 判据用测试，不用「模型自评」 | 自评会偏向自己；机检判据无法被讨好 |
| Verifier 独立、不读生成方思维链 | 同基座同盲区，只能靠对立利益与可执行反例补 |
| 结构性变更走 sandbox + diff + 人审 | 灰度与回滚的最小形态：先隔离，再合入 |
| 没有机检判据的任务直接拒接 | 否则「完成」变成修辞 |

## 4. 扩展点

- **接真目标树**：`xm/backlog.py` 从 `ROADMAP.md` 生成任务；下一步是让它读目标树而不是表格。
- **接真调度**：`sandbox/` + 复制项目 + 跑 daemon，产出 diff；再往上才是多任务并发与心跳常驻。
- **接异构验证**：换模型基座跑 Verifier，抓同基座盲区。

## 5. 已知限制（不藏）

1. 还不会自己找目标——任务目前从 `ROADMAP.md` 的表格里取。
2. 24h 连续运行未验证；无人值守只跑过单任务 2 轮。
3. 判据只能判「可机检」的部分；商业判断、审美、行业洞察都判不了，只能人判。
4. 推理模型（如 `deepseek-flash`）会把 token 预算烧在思维链上，预算不足时正文为空——daemon 已记录返回长度，但这属于"看得见还不够"的问题。
